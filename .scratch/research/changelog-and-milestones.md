### Does option (a), a hand-maintained and validated `curriculum/changelog.yaml`, match practice?

What the sources show:

- **Hand-curated, not taken from commits.** Every project surveyed writes its change record by hand. Keep a Changelog explicitly rejects commit-log changelogs. This supports rejecting option (c) as the source.
- **Dates can exist without tags.** roadmap.sh has kept a dated changelog since 2023 with no new tags. OSSU lists a version (7.2.2) with no tag. A per-event date that does not depend on tags or git is normal.
- **Structured, hand-maintained per-item data exists at scale.** BCD's `version_added` is the closest analogue to a per-route "ready since" field. It records when an item became available and is written by hand, not taken from history.
- **No surveyed project checks its changelog against current state.** The replay rule (the catalog must equal the replayed events) goes further than anything surveyed. OSSU shows what that rule prevents: curriculum changes ship "immediately" through RFCs, and its changelog has not recorded any since 2017.
- **Keep a Changelog layout compatibility.** "Unreleased first, then releases newest first, ISO dates" is Keep a Changelog's layout, and the RFC's generated `CHANGELOG.md` block can follow it. `promoted` / `added` / `removed` / `demoted` map roughly onto Added / Removed / Deprecated.

**Recommendation:** adopt (a) as written. It follows the common practice (curated by hand, dated, Unreleased first, readable by people) and adds one mechanism none of the references have: the replay check. **Confidence: high** that it fits practice. The validation rules are new to this repo and have no outside precedent to borrow from.

### Decision (a): what does "lab added" mean?

Repository facts (`git log --diff-filter=A -- labs/<id>`):

- The "directory created" commits in the RFC (`8612869`, `6d01785`, `ef4e543`, `3064954`, `1b93b82`) each add **only `README.md`**. The rest of each lab followed within seconds, in single-file commits with the same message:
  - self-attention: `starter.py` `d8ace6f` 09:14:05, `solution.py` `0560a39`, `tests.py` `24cf142` 09:14:09
  - evaluation-harness: `tests.py` `f1f7ebb` 09:14:19
  - model-selection: `decision-template.md` `25bda1c` 09:35:45
  - agentic-design: `decision-rubric.md` `519c435` 09:35:49
  - prompt-injection-boundaries: `tests.py` `dd142e5` 09:35:59
- So every lab met the practice-packaging contract in `AGENTS.md` (task, starter state, runnable checks, reference solution) and could run locally by about 09:36. The browser commits (`842684c`, `9daf4a1`, `82f4314`) added `lab.yaml`, which is the site's delivery contract ("Browser contract: the web atlas runs this lab in Pyodide"). Only `82f4314` changed the lab itself: it moved self-attention onto NumPy.

What the sources show:

- **Date the event by when learners can use the item.** BCD dates by the release a feature shipped in. Baseline dates by interoperability. Exercism hides `wip` items. freeCodeCamp counts only "live" items.
- **Record the delivery mode separately from the item's existence.** BCD adds a second support statement when a feature needs a flag. It does not move `version_added`.

**Recommendation:** define `lab-added` as the day a complete lab (the practice-packaging contract) lands on `main`, runnable from the repository. Browser runnability is a property of the site, already recorded in `lab.yaml`'s `browser` block, and is not a curriculum event. That is the RFC's proposal in substance, but the wording and evidence should change:

- Say "complete lab on `main`", not "directory created".
- Point `evidence` at the commit that completed the lab (for example `24cf142` for self-attention), not the README-only commit.

The backfilled dates stay the same, since everything happened on 2026-09-22. **Confidence: medium-high.** "When learners can use it" is a consistent pattern across the sources. Choosing the repository over the site as the learner surface follows this repo's own docs (labs run locally with `tests.py`). If the owner considers the web atlas the primary product, the date would move to the browser commit, which is still the same day.

### Decision (b): keep 0.1.0 as recorded, or tag it first?

Repository facts:

- `CHANGELOG.md` gained "0.1.0 — 2026-09-22 / Initial public repository." in `1dda52e` (08:29:07). `curriculum/manifest.yaml` with `version: 0.1.0` came in `78b4784` (08:29:23). They are 2 of 20 "chore: build curriculum repository structure" commits, spanning `3b8ae1d` 08:29:00 to `113a5f0` 08:29:59.
- In `1dda52e` itself, the "Unreleased" section already listed "Initial repository structure", "Curriculum and resource schemas", "Seed competencies…". 0.1.0 was declared in the same commit that called the repository structure unreleased. The record therefore names no commit as the 0.1.0 state.
- There are no tags (RFC 0021, finding list). `docs/VERSIONING.md` step 6: "tag the commit only after the release state is internally consistent."

What the sources show:

- Tagging after the fact is routine (Pro Git, "Tagging Later").
- Keep a Changelog's convention links each version to a tag, but the spec does not require one.
- Tags are missing for recorded versions in practice (OSSU 7.2.2, roadmap.sh after 4.0).
- SemVer forbids changing a released version's contents. A tag placed on a guessed commit would fix a claim about what 0.1.0 contained that the record does not support.

**Recommendation:** keep 0.1.0 in `releases` as recorded (2026-09-22, no events). Do not tag it retroactively unless the owner can name the commit that was public as 0.1.0. The RFC's validator does not read git, so nothing depends on a tag. Make the first tag `v0.2.0`, annotated and pushed explicitly, on the commit that cuts the first release through the new process, following `VERSIONING.md` step 6. If the owner wants a 0.1.0 tag anyway, the defensible commit is `113a5f0`, the last structure commit. That is an owner assertion, not something the evidence shows. **Confidence: medium.** The sources allow both options; the recommendation rests on the ambiguous repository record.

### Structural answers

1. **Title plus a short ask per milestone.** Every reference gives each step a title, and most give a one-line ask: Boot.dev chapter descriptions, CS50 "Problem to Solve", MS "Instructions". The RFC's `title` plus `ask` (at most 300 characters) is the common shape. **Recommendation:** keep it as proposed. **Confidence: high.**
2. **Linked skills.** No reference has a structured per-step skills field. Odin links inline, MS states goals at lesson or section level, and Made With ML lists none. `integrates` is therefore stricter than practice. It is justified by this repo's catalog-first rule and applied-integration check, not by any competitor. **Recommendation:** keep it. Outside practice gives no reason to relax it. **Confidence: medium.** There is no precedent either way.
3. **Evidence per milestone.** MS (a rubric per assignment) and CS50 (a `check50` slug per problem) attach evidence to each unit. Full Stack Open instead assesses the final state of one evolving app. **Recommendation:** per-milestone `evidence` as proposed. **Confidence: medium-high.**
4. **Show milestone numbers?** The pattern across the sources is to number by position in navigation (MS ordered lists, Boot.dev chapters, CS50 weeks) and to reference by a stable slug or path (CS50 `check50` slugs, Made With ML URLs, MS folder paths). Full Stack Open is the exception: it uses numbers as references (`1.3`). Its exercise numbers belong to a course that is re-edited as a whole. That matches the drift RFC 0022 found ("Milestone 6" pointing to the wrong section). **Recommendation:** adopt the RFC's approach:
   - no number in the README heading or the ID;
   - number by position in the page rail only;
   - cross-reference by `#<id>` or heading anchor.

   **Confidence: high.**

5. **Shared evidence across milestones (F8).** No reference lists one artifact under two units by name. Full Stack Open does accept one final artifact as satisfying several steps. The shared records come from one package stage ("Stage 3 — one controlled optimization"), so splitting them would misstate the package. **Recommendation:** keep the RFC's rule (an ID may appear in more than one milestone). Render the second occurrence as "shared with <milestone title>" so learners and reviewers don't count it twice. Assigning each record to one milestone is also defensible. Assigning each shared ID to the milestone whose package stage produces it is the owner's call, per the RFC. **Confidence: medium-low.** There is no direct precedent.
6. **Unplaced evidence (`experiment-results`, `decision-records`, `traces`).** In every reference, evidence belongs to a unit (an assignment rubric, a problem slug, a part submission). None keeps generic project-level evidence next to per-unit evidence. **Recommendation:** remove the three generic IDs, because each milestone already names its specific record. If the owner wants a project-wide artifact (for example a trace store used by several milestones), attach it to the milestone that first produces it. Don't bring back a project-level list, which the RFC's derived union correctly rules out. **Confidence: medium.**
7. **Content gaps F1–F7 and F9** (missing asks, missing route links, missing evidence IDs, a stale "Milestone 6" reference, "Round 1 failure analysis"). Competitors cannot answer these. They are curriculum decisions about this project's text and the catalog, and they need the owner, as the RFC says. This note does not try to fill them.
